# Выбор и настройка мониторинга в системе

## Мотивация
1. Пользователи теряют заказы. Нужно понимать где заказы теряются или застревают.
2. Сроки выполнения не соблюдаются. Нужно знать какой из компонентов системы влияет на это.
3. Высокий отклик на запросы к системе. Нужно понимать что тормозит и в какой момент
4. Любая система может порождать ошибки от незначительных до критических, которые могут внезапно влиять на систему. Их нужно учитывать и исправлять в порядке приоритета. Если приложение 500, то это hotrush, например. Исходя из этого выделять ресурсы на исправление.

## Выбор подхода к мониторингу
1. Для мониторинга MES подойдёт **USE**. Так как нам важно понимать, сколько времени тратится на расчёт стоимости как для сложных так и для простых моделей. Очевидно, что просчёт сложной модели поставит простые в очередь, так как у нас пока только один инстанс MES. Тут нужно будет понимать, что приоритетнее, посчитать за 30 минут 15 простых или одну сложную модель. Это поможет в реализации приоритетов для работы над моделями. Так же мы видим, что заказы недоходят до клиентов, а значит у нас где-то ошибки и мы хотим это знать
2. Для мониторинга отклика бэкенда на действия пользователей используем **Четыре золотых сигнала**. Наше приложение должно быть отзывчивое, а значит latency, traffic, errors, saturation имеют важное значение.

## Метрики
все эти метрики на dashboard

1. Number of requests (RPS) for API - важно знать сколько запросов отрабатывает каждый API
2. Number of dead-letter-exchange letters in RabbitMQ - так как унас асинхронное взаимодействие, то количество повторных отправлений RabbitMQ важная метрика, она говорит о том, что кто-то не может принять отправления
3. CPU % for MES API - тут на сложных моделях 30 минут расчёт. Надо знать почему, прогнозировать масштабирование
4. Memory Utilisation for MES API - это нагруженный сервис, хотим всё знать про него
5. Response time (latency) for API - низкая latency => лучший пользовательский опыт
6. Size of S3 storage - кончится место, и MES не сможет принимать новые заказы. Нужно смотреть, заранее расширять хранилище
7. Number of HTTP 500 API - если на 500, то надо чинить. Это причина потери заказов, срыв договорённостей, повышение dead-letter-exchange letters

## План действий
1. Установим Prometheus
2. Для визуализации - Grafana
3. В Grafana выведем на dashboard ключевые, по моему мнению, метрики
4. Настраиваем Grafana Alerting

## Показатели насыщенности
1. CPU % for MES API. Если втечении длительного времени CPU >= 100%, то это может означать о перегрузке инстанса, увеличению задач в очереди на просчёт. Нужно увеличить число инстансов.
2. Number of HTTP 500 - повод создать тикет, смотреть Sentry, в общем это потеря функциональности. Требуется расследование
3. Memory - если памяти нет, но используется свап, а это в 1000 раз медленнее. Следим, расширяемся. Если у нас 24/7 80% - есть повод реагировать
