# Планирование: анализ, идентификация проблем и поиск решений

## Существующие и потенциальные проблемные места

1. MES API и Shop API ходят напрямую в DB
2. В API есть ошибки которые приводят к потере заказов или к зависанию заказа в одном из статусов
3. Скорость расчёта MES. Так как инстанс один, то сложная модель, расчёт которой занимает до 30 минут, поставит полее мелкие в очередь, что в свою очередь ухудшит пользовательский опыт. 100% узкое месть системы.
4. Нет приоритизации в выполнении заказов. Это может привести к тому, что из за увеличения числа заказов, те у которых срок готовности истекает могут бытт взяты в последнбб очередь или не взяты вовсе.
5. Репликация DB. Читаем данные с реплики. Запись данных приоритетнее чтения. Если мы прочитаем немного устаревшие данные по состоянию заказа, то ущерб будет минимаен.

## Инициативы
в порядке приоритета

1. Добавить мониторинг.
2. Добавить КЭШ между MES DB, Shop DB и API
3. Масштабирование MES
4. Приоритизация заказов на исполнение

## Какой вы видите целевую архитектуру через полгода?
Масштабируемое отказоустойчивое приложение с низким временем отклика. Засчёт мультиплицирования MES, балансировки нагрузки и кэшем этого удасться достичь.

## Что бы вы выбрали и почему?
1. Мониторинг. Потеря уже созданых заказов это прямой убыток компании и репутационный ущерб. Это ограничивает возможности расширения бизнеса.
2. КЭШ. Пользовательский опыт улучшится. Современный интерфейс должен красивым, удобным, но и быстрым. Если компания в состоянии сразу ответить на запрос клиента, то это огромный плюс.
3. Приоритизация заказов на исполнение. Соблюдение сроков - основа договорных отношений.
