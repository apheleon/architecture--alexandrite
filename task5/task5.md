# Задание 5. Кеширование

## Мотивация
1. Долгая загрузка MES
2. Рост нагрузки => увеличение времени обработки запросов
3. Пагинация и фтльтрация не помогают
4. Клиенты и партнёры жалуются

Что кэшируем?
1. дашборд MES
2. новые заказы для опретора
3. расчёт стоимости изделия есть смысл кэшировать. не считать ещё раз то, что еже было посчитано
4. Shop - кэш для страниц моделями

## Предлагаемое решение

Применяем **Cache-Aside**. Сначала идём в кэш, если там нет идём в БД, кладём в кэш и отдаём клиенту. В нашем случае данные читаются часто, а обновляются редко, пока в всяком случае, например: список заказов в статусе MANUFACTURING_APPROVED.
Данный паттерн просто в реализации, именно это и нужно, нас наняли тушить пожар.
С ростом нагрузки, например много записей в базу - читая с кэша не будем блокировать запись.

**Write-Through** - сложен, может замедлить систему из за записи  в кэш и БД

**Refresh-Ahead** - сложно, мы только внедряем мониторинг. Некорректная реализация приведёт к ущербу

### Инвалидация кэша
1. По событию для критичных данных: новый заказ, статус
2. TTL. Информация по заказу может устареть. Если мы на минуту покажем старый стаус у заказа - ни чего страшного не случится.

### Стратегии инвалидации кеша для компонентов системы

| Компонент системы          | Стратегия инвалидации                     |
|----------------------------|------------------------------------------|
| Список заказов (MES)       | TTL 1мин + Инвалидация по событию   |
| Статус заказа              | Инвалидация по событию                   |
| Данные API (стоимость)     | TTL 5мин                          |

### Ещё варианты
Как я понял речь про разные варианты инвалидации.

|           | 1                     | 2|
|----------------------------|------------------------------------------|----------------------|
| Описание|TTL + Инвалидация по событию   | Инвалидация по событию|
| +     |актуальность vs производительности<br>TTL сам удалит устеревшие|все данные актуальны<br>кэш всегда наполнен свежими данными|
| -     |задержка обновления не критичных данных|высокая нагрузка<br>не эффективен для редкоменяющихся данных|

Гибридное решение больше подходит так как TTL для не критичных и события для критичных, снизит нагрузку при росте запросов, обеспечит компромис между актуальностью и производительностью.
